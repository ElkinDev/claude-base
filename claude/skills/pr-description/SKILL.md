# Pull Request - title + description (clean-code standard)

Produce a PR TITLE and DESCRIPTION as text and hand them off. Whether the human opens the PR or the
agent may is a project choice (the git discipline in your `CLAUDE.project.md`); the shipped default
is hand-off only. This skill mirrors and grounds the evidence pack's pr-comment file.

## House rules (defaults; a profile may relax them)
- Follow the project's git discipline. If it is hand-off only: never open, set, complete, approve,
  or comment on a PR. Output the title and description as text and stop.
- NEVER add `Co-Authored-By`, `Generated by`, or any AI attribution.
- English only. No em-dashes. Proposals framing: do not present work as shipped, validated, or live
  until it is merged and deployed.
- No person names on shared content ("Jane suggested", "ask the lead"). Describe the change, not who.
- Tables: some hosts (for example Azure DevOps) render markdown tables poorly, while GitHub and
  GitLab render them fine. Follow the profile; when unsure, default to bullet lists and `- [ ]`
  checklists so it reads well everywhere.
- If the change touches the front end and the profile requires a demo, the PR needs a demo video.
- Keep each paragraph on one continuous line (see "Paragraph style").

## Title
Format: `[<tracker-id>] <type>(<scope>): <imperative summary>`
- `type`/`scope` use the same Conventional Commits vocabulary as the `commit-message` skill.
- Imperative, <= 70 chars, no trailing period.
- The `<tracker-id>` prefix links the PR: an Azure DevOps work item id, a Jira key like `PROJ-123`,
  or omit it entirely for plain git with no tracker.
- With a squash merge the PR title becomes the commit subject, so keep it commit-quality.
Example: `1354 feat(invoices): add payment-type breakdown` (Azure DevOps), or
`PROJ-42 feat(billing): add payment-type breakdown` (Jira), or
`feat(billing): add payment-type breakdown` (plain git).

## Description structure (why first)
Google eng-practices: the first line states WHAT concisely (imperative), then the body explains WHY.
Link the item, describe the changes, request reviewers. Keep sections short, use lists. Drop any
section that does not apply.

1. Summary. One to three sentences: what this PR does. First sentence imperative.
2. Why / Context. The problem and motivation. Link the item (`Refs #<id>` or `Refs PROJ-123`).
3. Changes. The key changes and approach, as bullets. Call out generated files.
4. Impact areas. Endpoints, screens, or modules affected, and who is unaffected.
5. How to verify / Evidence. Tests run and the result, gates green, before/after numbers.
6. Screenshots / Demo. Required for UI when the profile asks for it. Reference the demo video by name.
7. Risks / Out of scope / Follow-ups. Breaking changes, deferrals, known gaps.
8. Checklist (`- [ ]`), tailored to THIS change, never a fixed list. Resolve the item id from the
   branch/task (never a hardcoded number) and link it. Common items: quality gates pass, evidence
   pack current, no secrets committed, item linked. Add an item ONLY when it applies to this diff (a
   demo video when the front end changed, a DB migration reviewed, a feature flag toggled). Omit
   what does not apply. Drop the whole section if it would only echo the gates.

## Paragraph style (how to wrap)
Do NOT insert line breaks inside a paragraph. Write each paragraph, bullet, or checklist item as one
continuous line that flows like a book paragraph; the host soft-wraps it. Separate paragraphs with a
blank line. No fixed width, single spaces between words, no trailing spaces. This pastes and reflows
cleanly in the PR description field.

## Workflow
1. Read the branch change: `git diff <integration-branch>...HEAD --stat` and the diff. Describe what
   it shows, do not invent.
2. Draft the title (tracker id prefix if any + Conventional Commits, imperative).
3. Fill only the sections that apply, why first, lists not tables, one continuous line per paragraph.
4. If the front end changed and the profile requires it, add the Demo section and flag the video.
5. Validate against the checklist. Hand off the title and description as text.

## Validation checklist (all must hold)
- [ ] Title: tracker id prefix (if any) + `type(scope)` + imperative summary, no period, <= 70.
- [ ] Why is stated and the item is linked.
- [ ] No em-dashes, English, no AI attribution, no person names. Tables only where the host renders them.
- [ ] Proposals framing for anything not yet merged and deployed.
- [ ] Front-end change references the demo video when the profile requires one.
- [ ] Each paragraph is a single continuous line, blank line between paragraphs.

## When to use
- When handing off a PR for a branch.
- When the user asks "arma el PR", "descripcion del PR", "titulo del PR".
- Pairs with commit-message (title vocabulary), quality-gates (green first), and evidence-report
  (this is the same content as the pr-comment file).
