# Commit Message - Conventional Commits, 50-char title, continuous-line body

Produce ONE well-formed commit message from the ACTUAL staged changes, then hand it off as plain
text. This skill writes the message. Whether the human commits or the agent runs `git commit` is a
project choice (the git discipline in your `CLAUDE.project.md`). The shipped default is hand-off
only: output the message and stop.

## House rules (these are the defaults; a project profile may relax them)
- Follow the project's git discipline. If it is hand-off only: never run `git commit`, `git push`,
  `git commit --amend`, or open a PR. Output the message as text and stop.
- NEVER add `Co-Authored-By`, `Generated by`, or any AI attribution in the title, body, or footer.
- English only. No em-dashes (use periods and commas). Imperative mood ("add", not "added"/"adds").

## The blueprint
```
<type>(<optional scope>): <short description>

<optional body: the WHY and WHAT, not the HOW>

<footer: the tracker link (per your tracker) + BREAKING CHANGE: ... if any>
```

## Types
| type | use for |
|------|---------|
| feat | a new feature for the user |
| fix | a bug fix for the user |
| docs | documentation only |
| style | formatting, no production code change |
| refactor | code change that neither fixes a bug nor adds a feature |
| perf | a change that improves performance |
| test | add or correct tests |
| chore | build tasks, package manager configs, tooling |
| build | build system or dependencies |
| ci | CI configuration |
| revert | reverts a previous commit |

Breaking change: add `!` after the type/scope (`feat(api)!: ...`) and a `BREAKING CHANGE:` footer.

SemVer mapping (Conventional Commits v1.0.0): `fix` -> PATCH, `feat` -> MINOR, any `BREAKING CHANGE`
(or `!`) -> MAJOR. Per the spec, the scope MUST be a noun naming a section of the codebase.

## Scope
Lowercase, one word, the area touched. Generic examples: `api`, `auth`, `ui`, `db`, `config`,
`deps`, `docs`, `ci`. Prefer the scope the neighbors in that folder already use. Omit the scope if
the change is broad.

## The seven rules (the craft behind 50/72)
Conventional Commits defines the STRUCTURE; the "seven rules of a great commit message" (Chris
Beams) define the craft:
1. Separate subject from body with a blank line. Git treats everything up to the first blank line as
   the title and reuses it in `git log`, `shortlog`, and `rebase`.
2. Limit the subject to 50 chars (readability, and it forces a concise summary).
3. Capitalize the subject. Nuance: Conventional Commits starts the subject with a lowercase `type`
   and keeps the description lowercase, so we follow Conventional Commits here. This is the one
   classic rule the structured format overrides.
4. No trailing period on the subject (wastes characters).
5. Imperative mood: "add", not "added"/"adds". Test: "If applied, this commit will <subject>".
6. Do not hard-wrap the body. The classic rule wraps at 72 for a terminal `git log`; we override
   that and write continuous-line paragraphs. See "Paragraph style" below.
7. Body explains WHAT and WHY, not HOW. The diff already shows how.

## Paragraph style (how to wrap the body)
Do NOT insert line breaks inside a paragraph. Write each paragraph as ONE continuous line that flows
like a book paragraph; the editor and most hosts soft-wrap it. Separate paragraphs with a blank
line. No fixed width (not 72, not any exact number), single spaces between words, no trailing
spaces. Tradeoff to accept: a raw `git log` in a narrow terminal will not re-wrap these long lines.
The title stays one concise line (<= 50). (If your project prefers hard 72-wrap, say so in the
profile and follow that instead.)

## Tracker link (footer, depends on your tracker)
- **Azure DevOps:** end with the work item id as a bare footer on its own last line, e.g. `#1412`.
  Azure DevOps uses this `#<id>` mention to link the commit to the work item.
- **Jira:** put the issue key in the footer (or subject) so the Jira integration links it, e.g.
  `Refs PROJ-123` or a leading `PROJ-123` in the subject, per your team's Smart Commits setup.
- **Plain git (no tracker):** no footer needed; reference an issue number only if the host uses one.

Read the tracker from the profile and apply the matching form.

## Workflow
1. Read the real changes: `git diff --cached --stat` and `git diff --cached` (or `git diff` if
   nothing is staged). Describe what the diff shows, do not invent.
2. Pick ONE primary `type` from the dominant change. If the diff mixes unrelated changes, say so and
   suggest splitting into separate commits.
3. Pick a `scope` from the touched area, or omit it.
4. Write the title <= 50 chars, imperative.
5. Add a body only if the change needs context (why + what), one continuous line per paragraph.
6. Add the tracker footer for your tracker. Add a `BREAKING CHANGE:` footer too if applicable.
7. Validate against the checklist. Hand off the final message in a fenced block.

## Validation checklist (all must hold)
- [ ] Title <= 50 chars, imperative, no period, valid `type`.
- [ ] Body (if any): one continuous line per paragraph, blank line between; explains why/what not how.
- [ ] English, no em-dashes.
- [ ] No AI attribution anywhere.
- [ ] Describes the ACTUAL diff, nothing invented.
- [ ] One logical change (else recommend splitting).
- [ ] Tracker link present in the form your tracker needs (or intentionally none for plain git).

## Example (Azure DevOps footer)
Imperative title (<= 50). Each paragraph is one continuous line, no breaks.
```
feat(auth): add password reset via email

Add a "Forgot password" flow that emails a signed, single-use reset link valid for 30 minutes. It reuses the existing mailer and token service, so there is no new dependency.

The endpoint rate-limits by email and always returns 200 so a caller cannot tell whether an address exists.

#123
```

## Bad -> good
- `Fixed stuff` -> `fix(auth): correct reset token expiry`
- `feat(auth): added a password reset flow that emails a link` (past tense, too long) ->
  `feat(auth): add password reset via email`
- `update code` -> pick a real type + scope and say what changed.

## References (recognized standards)
- Conventional Commits v1.0.0: https://www.conventionalcommits.org/en/v1.0.0/ (type/scope/`!`/
  `BREAKING CHANGE` structure and the SemVer mapping).
- Chris Beams, "How to Write a Git Commit Message": https://cbea.ms/git-commit/ (the seven rules).
- Tim Pope, "A Note About Git Commit Messages" (origin of the 50/72 convention).

## When to use
- Before handing off (or making) a commit for any branch.
- When the user asks "arma el commit", "mensaje de commit", "como quedaria el commit".
- Pairs with quality-gates (gates green first) and evidence-report (pack current).
