# Ledger, twice a day

`ledger-day.py` reads a time window of the Claude Code transcripts, the quota log written by the status line, and the merge commits of one repository, then appends one row per project to `<ledger>/ledger.md` and a full breakdown to `<ledger>/daily/`. The row answers three questions: quota points per merged feature, how much of the window went to waste (forks, status readers, narration turns, probes, cache breaks), and what the orchestrator context cost. The last one is two cells read from the main transcripts only: compactions with their rate per active hour and the peak before and floor after each one, and writing volume, the characters the session itself typed next to the characters it received back from its agents and its tools. The same two are pooled per side by `ledger-compare.py` and printed in the optimize list, whether or not they reach the top of the ranking. It builds nothing else: no brake, no alert, no notification.

Copy `ledger-config.example.json` to `ledger-config.json` and set the project mapping, the repository whose merges count and its branch. Point `CLAUDE_LEDGER_DIR` at the folder that holds `usage-log.csv` and will hold `ledger.md`. Python 3.12 or newer, no packages. The official `session-report` analyzer is used when it is installed under `~/.claude/plugins/marketplaces` and skipped with a message when it is not, in which case the cache-break bucket reports `not measurable` instead of a zero.

Register the two runs on Windows, as the current user and not as SYSTEM:

    schtasks /Create /SC DAILY /ST 08:00 /TN "Ledger\ledger-0800" /F /RL LIMITED /TR "powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\path\to\scripts\ledger-nightly.ps1"
    schtasks /Create /SC DAILY /ST 18:00 /TN "Ledger\ledger-1800" /F /RL LIMITED /TR "powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\path\to\scripts\ledger-nightly.ps1"

Verify with `schtasks /Query /TN "Ledger\ledger-0800" /V /FO LIST` and read `Next Run Time`.

On Mac and Linux the same two runs are cron entries; the window is computed from the clock the same way, so both lines are identical:

    0 8 * * * /usr/bin/python3 /path/to/scripts/ledger-day.py --since "$(date -d 'yesterday 18:00' '+\%Y-\%m-\%d \%H:\%M')" >> "$CLAUDE_LEDGER_DIR/nightly.log" 2>&1
    0 18 * * * /usr/bin/python3 /path/to/scripts/ledger-day.py --since "$(date '+\%Y-\%m-\%d 08:00')" >> "$CLAUDE_LEDGER_DIR/nightly.log" 2>&1

On macOS `date -d` does not exist; use `date -v-1d '+%Y-%m-%d 18:00'` in the 08:00 line. Percent signs are escaped because cron treats a bare `%` as a newline.

## Before and after

`ledger-compare.py` answers the question the rows alone do not: is the current way of working better or worse than the window before the change, in what and by how much. Freeze that window once with `python ledger-compare.py --freeze-baseline <ledger>/baseline.json` over a `ledger-day.py --json` payload of it, then every run renders `<ledger>/compare.md`: one table per axis (cost, speed, quality) with the columns `KPI | baseline | current | delta | verdict`, a recommendation, and the ranked list of what is left to optimize. Every KPI is a rate or a share, never a raw count, so two windows of different length stay comparable; the absolute totals live only in the header.

The `compare` block of `ledger-config.json` holds the baseline file and its label, the cap start that separates the two sides (sessions that began before it are printed in a `pre-cap` row, never counted), the thresholds a delta must reach to read better or worse, the minimum merged features a per-feature verdict needs, and the four evidence paths (gate exit files, landings, owner reports filed after a handoff, device kit). The nightly script runs the compare after the rows, so the page is never older than the ledger; on cron, add a second line calling `ledger-compare.py` right after `ledger-day.py`.

## Quality

A window that spends less is only a win if nothing got worse, so every run also computes three quality numbers over the same window with `quality.py` beside `ledger-day.py`: red gates by cause (the gate exit files, read through the installed `lane-state.py` and the `gates_dirs` of its config), review blocks (the rows of `landings.md` whose head carries REVIEW with BLOCK or CLEAR, and the ones it cannot place counted apart), and post-landing defects (the rows of `<ledger>/defects.md`, the landings whose subject starts with `fix`, and the fix lanes: every lane a landing carried, read from the reflog's previous tip to the landing on the first parent, is a fix lane when its own commits carry a `fix` subject and no `feat` one, which a train landing needs because its tip subject is the train's merge). They go to the Quality section of the daily breakdown and one row per run to `<ledger>/quality.md`, whose head unions the windows so a skipped run never reads as a quiet week. `landings.md` is read from the `landings` path of the compare block, else `EVIDENCE_ROOT`, else the `evidence` folder beside the repository. A landing is a move of the configured branch in its reflog, not a subject that reads like a merge, so a merge commit that only travelled inside a lane branch is never counted. Any source that is missing is printed as not measured with the reason; a failure inside `quality.py` becomes a note and the spend numbers still land.

## Trains and failed calls

Two short steps run between the compare page and the retention sweep, both read-only and both seconds long. `train-wait.py --row` appends one line with the trains of the last seven days, the lanes landed per train, the union gate runs per lane landed and the distribution of the hours from a lane's last CLEAR review to its landing, the move of main in its reflog, with the landings the reflog did not reach counted as timed by commit; it reads git and the evidence folder (`EVIDENCE_ROOT`, else beside the checkout) and nothing else, and a lane whose CLEAR review it cannot find is reported unmatched rather than as a zero wait.

`tool-errors.py --file <transcript> --row` runs over the two largest transcripts touched in the window, which are the seats, and appends one line each to `<ledger>/tool-errors.log`: the tool calls of the day, the failed ones, the share and the top four failure signatures. A failure is an `is_error` result or a line matched by `scripts/tool-errors.rules`, whose producer gate keeps a read of an old failure from counting as a new one. The point of both lines is that a defect class or a stalled train surfaces the same day, with nobody reading a pane.

Four more lines follow, each skipped with a log line when its script is missing: `token-shape.py --row` over the two largest main transcripts touched in the window (over 5 MB, in practice the seats) into `token-shape.log`, where the window's tokens went by kind; `rework-shape.py` into `rework-shape.log`, the gate runs, reds by phase and review rounds of the window; `tooling-block-rate.py --last-complete` into `tooling-block-rate.log`, one line per complete window, the BLOCK rate that keeps or reverts the hostile-input practice, run only when `TOOLING_BLOCK_ROOT` or `EVIDENCE_ROOT` names the reviews folder and `TOOLING_BLOCK_ANCHOR` or `TOOLING_BLOCK_FIRST_DECISION` names the practice's day; and `kit-twin-drift.py --row` into `kit-drift.log`, the kit twins that trail what the machine runs.

## Pulse

The last two steps read what the earlier ones wrote. `claude/tools/pulse.py` checks the register `pulse.md` in its evidence root (`PULSE_ROOT`, default `~/.claude`). The register has one line per adopted mechanism: its trigger glob, its use glob, the command that reads its number, the line that decides whether it stays, and a review date. The step logs each mechanism that is silent, dark or matching nothing, each one due for review, and each warning of this log that stands (three runs in a row) or recurs (three of the last fourteen). Every item carries a `pulse:<key>`, and the ledger hands the script this run's own log as `PULSE_LOG`. Then `claude/tools/pulse-escalate.py` takes every key flagged in both of the last two runs that no line of the rulings register cites. It writes them as one auto-class row in today's owner decisions file, the file `compact-recover.py` prints among the open asks at the next session start. A decision row citing the key closes it. Each step runs the installed copy in `~/.claude/tools`, the one the session-start hook runs, or the clone's `claude/tools` copy when that script was never installed, and is skipped with a log line when neither exists. `python ~/.claude/tools/pulse.py --help` gives the register format.

The session-start hook runs the pulse too, with no `PULSE_LOG`, so it finds this ledger's log only through `CLAUDE_LEDGER_DIR`. When the ledger stays in its default folder inside the clone, set `CLAUDE_LEDGER_DIR` to that folder in the user environment or in the `env` block of `~/.claude/settings.json`, the same setting `alarm-big-result.py` needs for its sizes file. Otherwise the block says `[pulse:log-missing]` and names the setting. A machine with no `pulse.md` sees no block at all.

## Retention

The morning run ends with a retention sweep, after the three steps so nothing the ledger reads is deleted before it reads it, and the run is told apart by the same clock test that picks the window, so neither scheduled task needs an argument. Rule A removes a `<scratch_root>/<project>/<session>/scratchpad` whose newest file at any depth is older than `scratch_days`, dating an empty one by its own folder stamp or the session folder's, whichever is newer, so a session that has written nothing yet survives, and takes the `<session>` folder with it when nothing else is left inside; rule B removes a subagent transcript under `<projects_root>/<project>/<session>/subagents` older than `subagent_days` by its own mtime along with the `agent-*.meta.json` sidecar of the same stem, sweeps a sidecar whose transcript is already gone on its own mtime, and never touches the main `<session>.jsonl` beside that folder or a memory folder. The four values live in the `retention` block of `ledger-config.json`.

Each rule logs one line to `<ledger>/nightly.log` with the counts and the bytes freed, deletes one item at a time so a file held open by a live session costs one error instead of the sweep, and skips a folder that holds a junction or a symlink. Check what a sweep would do with `powershell -NoProfile -File scripts\ledger-nightly.ps1 -RetentionOnly -RetentionDryRun`, drop it for a run with `-SkipRetention`, and cover it with `scripts/tests/test-ledger-retention.ps1`, which builds a fixture of old and new scratchpads and transcripts under TEMP and asserts the exact set of survivors. Rule A lists and removes a scratchpad through the long-path prefix, since a pad holding build output past 260 characters would otherwise be dated by the files Windows PowerShell can see and fail to delete; phase 5 of the test pins both.

## Worktree sweep

With a `worktree_sweep` block whose `repo` names a repository, the morning run then removes that repository's landed, clean worktrees through `claude/tools/worktree-sweep.py --apply`, oldest first and at most `limit` a run (30 by default). Before a worktree goes, its build evidence (`build/lockrun`, `build/precheck`, and every `reports` and `test-results` under a `build` directory) is written into one zip under `evidence_root`, and the zip is proven first: its entries are counted, their bytes are summed against a fresh walk, and every CRC is read back. An existing zip is never replaced; the next free name is taken. While any `*.lock.d` is held under `lock_root` the whole run is refused, and the first refusal stops it. The step runs python unbuffered, so a sweep killed at its 45-minute cap still logs what it printed. With `repo` null, the default, the step logs one line and does nothing. The step shares the retention gate, so a morning run with `-SkipRetention` or `-RetentionDryRun` skips the sweep too, with no `worktrees |` line. Check a sweep with `python claude/tools/worktree-sweep.py --repo <repo>`, a dry run that lists every worktree's class and what each zip would hold.

The page never invents a measurement: a KPI whose instrument did not exist in one of the two windows reads `n/m` with a footnote saying why, and quota points fall back to a labelled estimate from raw tokens when the window has no meter samples. `scripts/tests/test-ledger-compare.py` covers the four verdict states, the insufficient-sample path, a weekly meter that resets inside the window, and the pre-cap row.

## Evidence retention

With an `evidence_retention` block whose `root` names an evidence root, the morning run then removes the record work that root no longer keeps through `claude/tools/evidence-retention.py --apply`: round folders and record files older than two calendar months by their scope file, and, when the scope turns on its Android release rule, APKs more than ten releases behind the newest bundle. Removed files wait in `<root>-trash/<day>` (or `trash`) for the scope's `trash_days`, and every path goes into a manifest under `ledger/deleted`. Start the scope from `claude/tools/evidence-retention.example.json`, and name in `keep` every file a tool reads at run time. A root without its register file, a clock ahead of the machine, a trash it cannot use, a second run at once, or a plan past a quarter of the root's files refuses the whole run and removes nothing. The step logs its summary line and at most 20 error lines, and never runs on a dry retention run or with -RetentionOnly.
