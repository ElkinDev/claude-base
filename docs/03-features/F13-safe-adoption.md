# F13: Safe adoption

Satisfies: FR-003, FR-006, FR-045, FR-046, FR-047, FR-048. Stories: US-007, US-012. Depends on: ADR-002, ADR-004, ADR-009.

## Summary

The kit adapts to the repository and to the machine it lands on, never the other way round. Most adopters are employees whose company already defines instruction files, git hooks and lint wiring, and whose repository must keep working exactly as it did before anyone installed anything. So the installer knows which files it wrote, refuses to touch anything else, backs up before every write it does make, and ships a rollback that puts the previous state back. `install/lib.ps1` holds the ownership rule, `install/backup.ps1` holds the backup record, `install/adopt.ps1` holds what a repository already carries and how a run stays out of a shared history, `install.ps1` executes them, and `scripts/kit-restore.py` reverses them, with the reading and reporting half of the rollback in `scripts/kit_restore_report.py` beside it. F01 ports the same contract to `install/install.sh`, so the layout below is the shared one, not a Windows detail.

## Behavior

- Kit home: `$KIT_HOME` when set, otherwise `%USERPROFILE%\.claude`. The installer and `kit-restore.py` read the same variable, so a sandbox (a test, a second engine, a machine with a moved home) moves both at once.
- Managed-file manifest at `<kit home>/.kit-manifest.json`, format in `data-contracts.md`: one sha256 per absolute path, for user scope and project scope alike, written after every run that changes it and merged with the previous one. It is the only thing that lets the installer tell its own files apart from the adopter's.
- Ownership rule, applied to every file the installer wants to write. Target absent: write it and record the hash. Target present with the hash the manifest recorded: the kit wrote it and nobody changed it, so refresh it, after a backup. Target present with any other content, or with no entry in the manifest at all: it is somebody else's file, so back it up, leave it exactly as it is, write the kit version beside it as `<name>.new`, and print one line naming it. `-Force` turns that last case into an overwrite, still after a backup. A target whose content already equals the source is skipped silently, and recorded if the manifest had lost it: the bytes are the kit's, so the file is the kit's, and a record that was blanked, deleted or moved aside as broken is repaired by the first run after it.
- The `.new` proposal is not a side door: it goes through the same rule and is recorded in the manifest like any other managed file. A proposal the kit wrote and nobody touched is refreshed in place; a draft of the adopter's own that happens to sit at that name is backed up first and the replacement is printed as its own line. Nothing at either path is lost, and a rollback puts the draft back.
- Backups at `<kit home>/backups/<stamp>/`, mirroring the original absolute path with the drive letter as a folder, so a file at `C:\<rest of its path>` is kept at `<backup root>\C\<rest of its path>`, plus a `manifest.txt` of `trigger`, `overwritten`, `created`, `new` and `kept` lines. `created` records a file that did not exist before the run, which is what makes a full rollback possible; `kept` records a file the run deliberately did not write, so a restore knows to leave it alone. Each line is appended and flushed before the write it describes, and the folder is created on the first line, so a run that changes nothing leaves no folder and a run that dies halfway still leaves a record the rollback can read. The stamp is never one an existing folder already carries: two runs inside the same second get a folder each.
- `-DryRun` prints the plan, one line per file with its action (`write`, `refresh`, `backup+new`, `kept`, `draft`, `force`, `skip same`, `create dir`), and writes nothing at all, not even the manifest.
- Project scope (`-Project <path>`) opens with an adoption preflight that lists what the repository already has and what the installer will do about it: `CLAUDE.md`, `AGENTS.md`, `.claude/`, `.cursor/`, `.github/copilot-instructions.md`, non-sample `.git/hooks/*`, `core.hooksPath`, `.husky/`, `.pre-commit-config.yaml`, `lefthook.yml`, `CODEOWNERS`, `CONTRIBUTING*`, `.editorconfig`. The installer writes only `CLAUDE.md`, `CLAUDE.project.md` and `.claude/`, plus `docs/` when `-Sdd` is passed, and the preflight names that fourth path only on the runs that write it; it never writes git hooks, CI files, or anything else in the repository.
- `-LocalOnly` (project scope) appends to the repository's exclude file exactly the paths this run manages inside the project, derived from the run itself rather than from a fixed list: what it wrote, and the `.new` proposals it left beside the adopter's files, with everything under `.claude/` folded into one line. A file of the adopter's own is never in there, so the switch cannot hide their work from them, and it never writes a blanket `*.new`. The file it appends to is the one `git rev-parse --git-path info/exclude` names, which is the only answer that holds for a plain repository, a worktree and a submodule alike; the file is created when absent and a line is never duplicated. Every project run ends by recommending the switch and by telling the adopter to check the team's policy on AI tooling before committing any kit file.
- `scripts/kit-restore.py`: `--list` shows every backup with its stamp, entry count and trigger; `--stamp <stamp>` restores the overwritten files, removes the created ones, drops their entries from the manifest, reports the `kept` files as untouched, and leaves the `.new` proposals in place, naming them. `--dry-run` prints the same actions and writes nothing. A file the manifest records and the adopter changed after the backup is skipped with the reason and the run exits 1; `--force` acts on it anyway. A file the manifest never got, which is what a run killed from outside leaves, is restored from the copy in the backup, and a `created` file in that state is removed only after a copy of it goes into the backup folder: the line in the backup is then the record, and the rollback still takes nothing away for good. A `manifest.txt` with no line it understands, and a stamp folder with no `manifest.txt` at all, are argument errors: each says so in words and exits 2 rather than reporting a rollback of nothing.
- No file the adopter has is ever opened for writing by the rollback. Every write goes into a temp file in the target's own folder and is renamed over the target, the managed-file manifest included, so a write that cannot finish costs the temp file and leaves the target byte for byte as it was. This is what makes the "named and stepped over" promise true for a file another program holds: the old shape opened the target first and emptied it before the failure was noticed. A rename that is refused takes the temp file with it, its read-only mode cleared first when the target had one, so a rollback run twice over a file it cannot replace leaves nothing of its own behind.
- `settings.json` is rendered from the resolved kit home, so the hook commands inside it point at the tree the run actually wrote, not at `%USERPROFILE%\.claude`.

## Edge cases

- Manifest missing or broken: every existing file counts as the adopter's, so the run degrades to backup plus `.new` instead of overwriting. Broken is anything that is not a map of path to hash: bad json syntax, an empty file, a file holding only a BOM, valid json that is an array, a `files` value that is not an object, an entry whose value is not a string. All of them are moved aside to `.kit-manifest.json.broken-<stamp>` and the run starts a fresh record, saying both out loud; it never crashes and never deletes what it could not read. The wrong answer here is a lost file, not an extra `.new`.
- A record lost after the install (deleted, emptied, moved aside as broken): the next run finds every kit file byte for byte its own, writes none of them, and puts them all back on the record. Without that, the record would stay at nothing and the rollback of the run that installed those files would no longer be allowed to remove them.
- A file the adopter deleted: absent target, so it is written again and recorded as created.
- A `.new` proposal already holding the kit version: nothing is written, so a re-run over a file the adopter has adopted is a true no-op, with no backup folder and, when the record still holds the proposal, no manifest rewrite either.
- Re-running after `git pull`: managed files that nobody touched are refreshed; the rest keep the `.new` treatment. FR-005 holds.
- A file changed after the backup: never restored silently. The restore names it, exits 1, and points at `--force`.
- A file the rollback cannot read, because something holds it in a way that refuses the read: it cannot compare, so it cannot know whose bytes are there, and a plain run skips it saying exactly that and points at `--force`. With `--force` the rename goes ahead, since replacing a file never required reading it, and the file is named as locked or unreadable only when the rename itself is refused. Under both shapes of hold, a byte range lock over a shared handle and a handle that shares nothing at all, that is what happens, and the file ends the run with the size and the content it started with. A read-only target refuses the rename the same way.
- A run that dies mid-plan, on a locked file or a denial: the exit code is non-zero, the summary says `STOPPED`, and the backup folder already names every file replaced up to that point, so the rollback puts them back.
- A run killed from outside (Ctrl+C at the console, `Stop-Process`, a closed window): nothing is printed and the managed-file manifest is never written, but the backup folder holds every line written until then, `--list` shows the stamp with the files it holds, and rolling it back restores them from the copies beside those lines.
- `.git` as a file (a worktree or a submodule): the exclude lines go to the common directory git actually reads, because the path comes from git itself. No git directory at all: `-LocalOnly` says so and skips, and nothing else in the run changes.
- Rollback of a project scaffold: files created inside a repository are removed one by one, the adopter's own files are reported as kept and never touched, and no folder outside the kit home is ever pruned.

## Out of scope

Uninstall automation beyond a single backup rollback (FR-007 keeps its documented manual list), merging a `.new` proposal into an existing file (a human reads both), restoring several backups in one call, and any behavior of the company's own hooks or CI, which the installer only reports and never drives.

## Acceptance

- `scripts/tests/test-install-smoke.ps1`, user scope, fourteen phases: fresh install writes the manifest; a re-run is byte for byte a no-op; `settings.json` follows `KIT_HOME`; a file edited by hand is recorded as kept, never as overwritten; three runs over an adopter-owned file leave one backup folder at most and a stable tree hash; a `.new` draft of the adopter's own is backed up and comes back; `-DryRun` leaves the tree hash unchanged; `-Force` overwrites after a backup; a rollback puts the edited file back and removes what the run created; an unreadable manifest is survived and moved aside; a run that dies on a locked file still leaves a record the rollback can read; two runs inside the same second never share a folder; and every shape of a broken record (empty, BOM only, an array, a one element array wrapping the record, a missing version, a version from another engine, a `files` that is a string, a hash that is not a string, a path that is not absolute, a path with a root and no drive, a path with a drive and no root) is called out, kept beside the fresh one, and replaced by a record that names every kit file again.
- `scripts/tests/test-install-project.ps1`, project scope, nine phases: a repository with its own `CLAUDE.md`, `docs/README.md` and pre-push hook keeps all three; `-DryRun` leaves the repository and the kit home byte for byte; `-LocalOnly` with `-Sdd` hides everything the run wrote, `docs/` included, asserted with `git check-ignore` and an empty `git status`; a second `-LocalOnly` run adds no line; the adopter's own files stay visible while the proposals beside them are hidden; in a worktree the lines land in the common directory and git ignores them there; a project rollback exits 0 and leaves the company files alone; a `CLAUDE.md` that is byte for byte the kit's is reported as already matching, with no `.new` promised that the run would not write; and a source folder gives up only the files the kit ships, never the bytecode caches or the `.bak` and `.new` files a clone happens to carry.
- `scripts/tests/test-kit-restore.py`, fifteen cases against hand built backup folders for the everyday paths: listing, restore, removal of created files, `kept` entries left untouched by a plain run and by `--force` alike, the modified-after-backup refusal and the `--force` that overrides it, a dry run that writes nothing, and an unknown stamp reported as an argument error in words.
- `scripts/tests/test-restore-failures.py`, fourteen cases for what a rollback meets when it cannot do what the record asks: a created file and an overwritten file held open by another program are named and stepped over while the entries after them still run and the exit code turns 1; four cases hold a file the adopter edited after the install under both shapes of hold, with and without `--force`, and assert the size and the content of that file after the run, which is the assertion that catches an implementation that opens the target before it knows it can finish; a read-only target, which refuses the rename with nothing holding it, is rolled back twice and the folder is asserted to hold no temp file of the rollback's afterwards; an unparseable `manifest.txt` and a folder with no `manifest.txt` are argument errors in words; and the state a killed run leaves (backup lines written, managed-file manifest untouched) is restored from the copies, with the created file copied into the folder before it goes and the line saying where that copy is and whether the bytes are still the ones the run wrote. The fixture both restore suites build on is `scripts/tests/lib-restore-test.py`.
- `scripts/tests/test-install-rollback.py`, two cases that drive `install.ps1` itself: a run that kept the adopter's file rolls back without touching it, and a run made after the record was lost puts every kit file back on the record, so the first run's rollback still removes what it created.
- Every phase asserts the installer's exit code, and both PowerShell suites run against a sandbox home under `TEMP` that they refuse to leave.
- No path outside `CLAUDE.md`, `CLAUDE.project.md`, `.claude/` and, with `-Sdd`, `docs/` is written in project scope, asserted by the untouched company hook and the untouched `docs/README.md` in the project suite.
