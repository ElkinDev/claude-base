# F16: Reserve mode

Status: proposal. The tool, its law file, the skill section and the tests are in the tree; nothing is reviewed or merged, and no FR covers this channel: the requirement is proposed with the feature.

Stories: US-013, the operator running a long queue under a subscription cap. Depends on: ADR-005, whose declared scope is the hooks and the statusline, so a kit tool ships as a pair the way `wait-marker` already does, and ADR-006, portable paths: every default is `~` or a profile variable, never an absolute personal path.

## Summary

The orchestrator pane is normally the planner: it runs on the planning model, holds the context and decides. When that model's weekly meter is nearly spent the whole train stops for a resource that only planning and adjudication actually need. Reserve mode separates the two. The pane switches its own runtime to a cheaper model with `/model`, keeping its context and its launch line, and buys planning back one call at a time: a packet in, a plan or a verdict out, no session, no tools, no history.

The pattern was verified against the installed CLI on 2026-09-03. The flags it rests on, `--print`, `--model`, `--effort`, `--tools`, `--no-session-persistence`, `--permission-mode`, `--output-format` and `--system-prompt-file`, all exist, and one smoke returned exit 0 with a single json object carrying `subtype: success`, the answer in `result`, and a usage block whose `cache_creation_input_tokens` was 2940. Those 2940 tokens are the user level instructions the CLI always loads, which is why the tool runs from an empty directory: a project `CLAUDE.md` in the working directory would be billed on top of them on every call.

## The tool

`claude/tools/ask-planner.sh` and `claude/tools/ask-planner.ps1` are one contract in two halves, installed to `<kit home>/tools` by the same `Get-KitPairs` pattern that already copies `record.py` and the `wait-marker` pair.

- Usage `ask-planner.sh [-o <answer file>] [<packet file>]`; no packet file, or `-`, reads the packet from stdin. Windows PowerShell rejects a bare dash in its own argument binder before `-File` hands anything to a script, so a caller on that host omits the packet instead of writing `-`. From a POSIX shell, Git Bash on Windows included, the call is `sh "$HOME/.claude/tools/ask-planner.sh" -o <answer> <packet>`; typed in PowerShell it is `powershell -NoProfile -File "$HOME\.claude\tools\ask-planner.ps1" -o <answer> <packet>`, and from another shell that path is spelled in full, because `-File` does not expand `~`.
- Defaults, all overridable by environment and none by a flag: `PLANNER_MODEL` `claude-fable-5-1`, `PLANNER_EFFORT` `xhigh`, `PLANNER_LAW` the law file beside the script, `PLANNER_LEDGER` under the profile's `.claude/ledger/`, `PLANNER_BIN` `claude`. The model and the effort stay out of the flags on purpose: the planner runs at `xhigh` or `max`, and a flag makes lowering it a typo away.
- The call is always the same line, `--print --model --effort --tools "" --no-session-persistence --permission-mode dontAsk --output-format json --system-prompt-file`, with the packet on stdin, stderr passed through untouched, and the working directory one the call gets to itself: a directory made new under `<temp>/planner-cwd/`, named with the pid and a random suffix, and removed on every way out. It is empty because it is new, which is what keeps a `CLAUDE.md` left there by anything else from being loaded and billed as cache creation on every call from then on. Emptying the shared folder instead would delete files the tool never made and would give two calls at the same time one directory.
- Because the call runs from that scratch folder, every path the tool is given or derives is rooted first, once, against the directory the caller stood in: the packet, the answer file, the ledger, the law, and the script's own name, which is where the default law comes from. A first real call on 2026-09-03 proved the point, invoked as `sh claude/tools/ask-planner.sh` from a repository root: the law path stayed relative and the CLI answered `System prompt file not found` from the scratch folder. On Git Bash the rooting also gives each path its native spelling, since `pwd` there answers with an msys path that a Windows program reads as a drive relative one.
- Exactly one call per invocation and never a retry. What a failure means is the caller's decision, not the tool's.
- Exit 0 prints `result` to stdout byte for byte and nothing else, so an orchestrator can redirect it into a file and diff it. Exit 1 is a failed call, with the model's own message or the raw output on stderr. Exit 2 is usage: an empty packet, a packet over 65536 bytes, a packet file that cannot be read, a law file that is not there, an answer file that names a directory or sits under one that does not exist, or a ledger that cannot be opened for append, each with one usage line, no call and no ledger row. Everywhere the answer has to land is checked before the call, because the call is the money: the ledger's folder is created and the file is opened for append first, so a mistyped `-o` or an unwritable ledger costs nothing.
- The answer goes to stdout first, then the `-o` file, then the ledger row. The call is already paid for by the time any of that runs, so bookkeeping never costs the caller the answer: a write that fails names itself on stderr in one line and the exit is 1, with the answer already on stdout. An answer file that fails then, because the place went away during the call, still gets its row, with an empty `answer_file`: the call happened, and the ledger is what records what it cost.

## The law

`claude/tools/planner-law.md` is the system prompt the call passes with `--system-prompt-file`, and it is the only standing instruction the planner receives. Three paragraphs: what the role is and that it never implements, what each packet kind must return (PLAN a numbered task graph with owners, owned files, verification commands and stop conditions, ADJUDICATE a CLEAR or a BLOCK with graded findings, DECIDE one recommended option and its fallback), and the output rules (DECISIONS, then GRAPH or VERDICT, then RISKS, then QUESTIONS, nothing else, under 1200 words). It also forbids trusting an unevidenced claim: the planner marks it unverified and puts its verification into the graph or the verdict.

## Packet discipline

The packet's first line is its kind. Under it come the objective, the numbered acceptance criteria, the workspace facts, the constraints and protected files, an evidence digest of report tails and disposition lines, the callable menu of roles and installed tools, the concurrency limit and the preferences. Under 20 KB, no transcripts, no diff over 200 lines. At most three calls per objective, from the orchestrator only, with packets and answers kept under `<evidence>/planner/`. The rules themselves live in one place, the `wave-orchestration` skill under "Reserve mode"; this file points at them rather than restating them.

## The ledger

Every successful call appends one row to `PLANNER_LEDGER`, a csv of its own and not the usage log, created with its header when missing: `time,model,effort,packet_bytes,input,cache_create,cache_read,output,thinking,duration_ms,cost_usd,answer_file`. The numbers come straight from the envelope's `usage`, `duration_api_ms` and `total_cost_usd`. Fields are never quoted, so a comma inside one becomes a space, and both halves write LF, so a machine that runs each of them at different hours reads one file rather than two shapes of it.

## Tests

`scripts/tests/test-ask-planner.py` runs 73 cases, one shared table answered by both halves plus one that pins a Windows host limit. The stub is named `claude`, placed first on `PATH`, and it records the argv it was given, the directory it ran from, what that directory held at the time, the bytes it read on stdin, and whether the file behind `--system-prompt-file` opened from that same directory the way the CLI opens it, which it reports as `law_readable` and then exits 3 when it could not. Two knobs make the failures the tool has to survive: one has the stub answer before it reads a byte of the packet, another has it remove a directory mid call. The cases pin the exact flag list and the environment overrides, the packet arriving from a file and from stdin, a packet that is not ascii arriving whole and counted in bytes rather than characters, stdout equal to `result` byte for byte on a two line answer with a currency sign, `-o` holding the same text, a working directory that is a scratch folder with no `CLAUDE.md`, the ledger header plus a row carrying 2940, 3153 and 0.05902 from a canned envelope shaped like the smoke, a second call appending without a second header, nine usage errors that make no call at all, among them an `-o` naming a directory, an `-o` under a folder that is not there and a ledger whose folder is a file, and four failure shapes: a non-zero exit, `is_error` true, a subtype other than `success`, and output that is not json, each leaving the ledger file there and empty. Four cases cover the path rule: each half called by a relative script name from a directory of its own, with a relative packet, a relative `-o` and a relative `PLANNER_LEDGER`, each half given a relative `PLANNER_LAW`, each half given a spelled out relative `PLANNER_BIN`, and each half given an absolute one in a folder that is not on `PATH` at all, with the shim on `PATH` moved away so no lookup could have found it. One case plants a `CLAUDE.md` in the shared folder, points the tool's temp there, runs twice, and reads the stub's own listing to prove each call stood in a child of its own, empty at the time, gone afterwards and never the same directory twice, with the planted file still there. Two more make the bookkeeping fail on purpose, the stub taking away the `-o` folder and then the ledger folder during the call, and assert the answer is on stdout anyway, the exit is 1, stderr is the tool's own single line rather than a stack, and the row is still written with an empty `answer_file` when it is the answer file that was lost. No case reaches the real CLI.

## Proof plan

No project relies on the mode until one pilot objective has run through it end to end and three things hold: the same number of review rounds to CLEAR as a comparable objective planned in the pane, or at most one more; cost per landing at least halved against the pane's own figure for that objective; and no defect reaching past the merge. Until that pilot is on record this is a tool in the tree, not a way of working.

## Out of scope

A packet builder. The packet is assembled by the orchestrator out of what it already holds, and a script that walked the repository to build one would either read more than the digest allows or guess at the objective.

## Acceptance

- Both halves answer the same table in `scripts/tests/test-ask-planner.py`, and no case in it reaches the real CLI.
- A fresh `install.ps1` run lands `tools/ask-planner.sh`, `tools/ask-planner.ps1` and `tools/planner-law.md` at the kit home.
- `scripts/sanitize-check.py` reports zero findings over the new files.
- The `wave-orchestration` sheet carries the trigger, the call, the packet shape, the budget, the evidence rule and the standing verdict rule in under 30 lines.
