# F10: Sanitization guard

Status: built 2026-08-28.

Satisfies: FR-040, FR-041, FR-042 (deny list part). Stories: US-008. Depends on: ADR-007, ADR-009.

## Summary

The tooling that keeps the repo generic forever: one checker with committed generic rules plus an untracked private denylist, wired as a local pre-push hook, with the pre-commit hook optional. The CI job that would run it on every push is F11 and is not built yet, so today the guard is local only.

## Behavior

- `python scripts/sanitize-check.py [--staged|--all|--range A..B|<paths>]`: scans text files and the names of the files themselves, reports findings as `<rule-id>: <file>:<line>` with the matched fragment, and exits 0 when clean, 1 on findings, 2 on usage or a hard failure. `--staged` covers the pre-commit case; `--all` scans every tracked file; a path argument scans that file or folder. `--messages-only` narrows a range to its messages and ref names, and `--json` prints the same result for a script.
- `--range A..B` covers the pre-push case. The right side is resolved to an object first, because a ref does not have to be a branch: an annotated tag is scanned whole, header block and message together, so the tagger identity a tag carries is read as well, and then the object it points at is scanned in turn, a tag at a time until the chain ends. What that chain ends at decides the rest. A commit runs the range: every commit the push would publish, each commit's message, every path those commits add or modify, the contents behind those paths, and the ref names passed with `--ref-name`, which the hook fills from the refs git is actually pushing. A tag pointing straight at a blob or a tree publishes no commit at all, so there is no range to walk: the blob is scanned under the label `blob <sha>`, and a tree is walked with `ls-tree -r -t`, every entry under it name-scanned and every blob read. `-t` is what keeps the directory entries themselves, which `-r` alone collapses: an empty subtree and a submodule publish a name and no content, and the name is where a forged tree hides a term. Tag objects are labelled `tag <sha>` and never by the ref name, since the name itself can be the leak. Names and contents are collected separately: every path is name-scanned, while contents are read once per unique blob sha. That split is what makes a rename safe, because two paths sharing one blob would otherwise let the second name through unscanned, and a file added and deleted again inside the range is still scanned. A path under `.sanitize/` among those objects is not skipped but rejected, exit 2 naming the commit and the path and never the contents, because a commit that carried the denylist keeps carrying it after a `git rm --cached` and the working tree looks clean while the push publishes every term. An all-zero remote sha, or one this repository does not have, falls back to every commit that is on no remote, and the fallback prints a notice rather than passing quietly.
- Committed generic rules (`scripts/sanitize-rules.txt`), one per line as `id<TAB>regex` with an optional third column of flags: personal home paths on any OS (`C:\Users\<name>`, `/Users/<name>`, `/home/<name>` where `<name>` is not a sanctioned placeholder, with the Windows rule matching any run of backslashes, so the one-backslash shell form, the two-backslash JSON form and the four-backslash form of JSON inside JSON are all caught), email addresses, tracker and forge org URLs that are not placeholders in both their https and ssh forms, and credential shapes (private key headers, connection strings carrying a password, bearer-like tokens, AWS access key ids, GitHub tokens, Slack tokens, and long `api_key` values). A rule flagged `name` is applied to path components as well as to line contents.
- Committed allowlist (`scripts/sanitize-allow.txt`): sanctioned placeholder users (`you`, `user`, `username`, `yourname`, `your-name`, `%USERNAME%`, `$USER`), placeholder orgs and domains (`your-org`, `example.com`, `example.org`), the GitHub noreply domain, and the two orgs this repo cites, its own and the third-party project in the vision doc. An entry clears a finding only when it full-matches the `name` group the rule captured, which is the user in a home path, the domain in an address, or the org in a URL: `you` does not clear `you-know-who` and `example.com` does not clear `example.com.attacker.io`. A rule that captures no name, which is every credential shape, can never be cleared this way. Org-level entries are a deliberate tradeoff: a private repository under one of those orgs would not be reported, so they stay limited to orgs whose repositories are public.
- Private denylist: `.sanitize/private-denylist.txt`, gitignored (the `.gitignore` entry ships in this feature). One term or `regex:` line each. A literal term matches case-insensitively across the shapes a name is written in, treating a CamelCase hump, a digit and an underscore as boundaries, so one term covers `AcmeViewModel`, `ACME_API_ID`, `acme-app`, `XAcmeClient`, `v2AcmeClient` and `ACMEapp` without matching `acmeish` or `ACMEISH`. When present the file is merged into the rule set with ids `private-<n>`. A CI runner never has this file. A `regex:` line that does not compile is a hard failure that names the rule and nothing else, since the pattern text and the message Python builds from it both carry the term, and no redaction is possible at that point because the redaction rules are exactly what failed to load.
- The output is publishable by construction, because it is read on screens and pasted into reviews. A private finding prints its rule id and location and no fragment. A generic finding on a line that also matches a private rule prints `redacted` instead of its fragment, so a rule cannot echo through another rule's match. A path whose name matches a private rule is reported once as `private-path: <redacted path> (private-<n>)` and every later finding in that file uses the redacted label. Waiver reasons are never printed. The `.sanitize` folder is never scanned in any mode, and in a push it is a hard failure rather than a skip. A reader that closes the pipe partway through the report, a pager or a `head`, ends the run at 1 with no traceback and no ignored-exception block, which is why the report writes are wrapped and stdout is pointed at the null device before the interpreter's last flush.
- Wiring: `python scripts/sanitize-check.py --install-hook` writes `.git/hooks/pre-push` from `scripts/git-hooks/pre-push` (add `--pre-commit` for the staged check as well). It is non-destructive: a repo whose `core.hooksPath` is managed elsewhere, or one whose pre-push hook is not ours, gets the exact line to add printed and nothing written. `--uninstall-hook` removes only hooks carrying our marker. The pre-push wrapper reads git's stdin, skips a deletion, passes both ref names to the checker, and does not echo them itself, because a branch name can be the leak. The CI job that would run `--all` on every push and PR is F11 and is not built yet.
- Meta-rule enforced by review, restated in CONTRIBUTING: the private names appear nowhere in the repo, including this feature's own files, commit messages, and branch names.

## Edge cases

- Binary files: skipped with a notice on a NUL byte in the first 8 KB. A NUL byte in a file whose extension says text, or in an extensionless file under 64 KB, is instead the finding `binary-in-text: <file>` and the file is scanned anyway, because that is the shape of a leak hidden from a text scan rather than a real binary. Files over 2 MB: skipped with a notice.
- False positives in third-party quoted material: per-line waiver comment `sanitize-ok: <rule-id> <reason>`, counted and listed in the output so waivers stay visible; the reason is written for whoever reads the file and is never printed. The waiver id `all` is the whole-file one and is honoured only on the first non-empty line of a file under a `fixtures` directory, where it skips the generic rules for that file and the summary reports how many files were skipped that way. Anywhere else, or below the first line, it is the finding `waiver-abuse: <file>:<line>` and the file is scanned regardless, so the whole-file waiver cannot be used to silence the guard. No waiver of either kind suppresses the private denylist. Those rules read every line of every file, fixtures included, because a fixture is the obvious place to park a real name, and a per-line `sanitize-ok: private-<n>` is itself reported as `waiver-abuse` with the finding left standing: a waiver is a claim that a generic rule matched something harmless, and nobody gets to make that claim about a private name.
- Known limitation of a literal denylist term: an all-caps spelling glued to more capitals, `ACMEAPP` or `MYACME`, is not matched. It cannot be separated from an ordinary word by any boundary rule, since `CACHED` carries `ACHE`, and matching it would fire on unrelated text. An all-caps term glued to a capitalised word is matched, because `ACMEApp` and `ACHEPoint` break at a capital that starts a new CamelCase word and ordinary English does not. The remedy for the rest is an explicit `regex:` line on the denylist for the glued constants a project actually uses.

- A denylist `regex:` line is refused when a quantified group is itself quantified, `(a+)+` and its relatives: Python's `re` has no timeout, and that shape backtracks long enough on an ordinary line to hang the hook and the push with it. The refusal is a hard failure naming the rule number, never the pattern. The remedy is to rewrite it as an alternation or as a literal term. An alternation whose branches overlap, `(a|a)+`, backtracks the same way and is refused by nothing, since no static check can tell two overlapping branches from two useful ones; it is documented in INSTALL.md as the second shape to avoid.
- The denylist file itself must never be committed: anything tracked under `.sanitize/` is a hard failure (exit 2) in every mode, before any scanning happens. A path argument pointing into `.sanitize/` is a hard failure for the same reason, since scanning it would put the terms in the output. Clearing the index is not enough once it has been committed: a range or a tree that publishes such a path is itself a hard failure, and the message says to rewrite the history.
- A path argument that does not exist is a hard failure rather than a silent zero-file pass, and git failing at any point prints what git said as a `notice: git ...` line and exits 2, so a scan never reports clean because a command did not run.
- The hook fails closed: a missing checker or no Python 3.8 or newer blocks the push rather than waving it through, because a guard that passes when it cannot run is not a guard.

## Implementation notes (2026-08-28)

Language: the checker is Python and only the hook wrapper is sh. `scripts/doctor.py` already makes Python 3.8+ a hard requirement of the kit, so a Python checker adds no dependency, while portable regex, binary detection and the denylist merge are unreliable across BSD and GNU grep, which is exactly the portability problem this feature exists to avoid. Git runs hooks under sh on every OS, Git for Windows included, so the wrapper stays sh; it probes `py -3`, `python` and `python3` in that order and keeps the first that answers version 3.8 or newer, because on Windows `python3` is usually the Microsoft Store stub, which exists on PATH and runs nothing.

Location: `scripts/`, where the rest of the kit's tooling already lives; the repo has no `tools/` directory. The files are `scripts/sanitize-check.py`, `scripts/sanitize_git.py`, `scripts/sanitize_guard.py`, `scripts/sanitize_rules.py`, `scripts/sanitize-rules.txt`, `scripts/sanitize-allow.txt`, `scripts/git-hooks/pre-push`, `scripts/git-hooks/pre-commit`, the suites `scripts/tests/test-sanitize-check.py`, `scripts/tests/test-sanitize-redaction.py`, `scripts/tests/test-sanitize-objects.py` and `scripts/tests/test-sanitize-hooks.py` over the shared sandbox in `scripts/tests/sanitize_case.py`, and the fixtures under `scripts/tests/fixtures/sanitize/`.

Four Python modules rather than one, to keep each under the 300-line limit of NFR-003: `sanitize-check.py` is the command (flags, hook install, output), `sanitize_guard.py` holds the scan and the scan modes, `sanitize_git.py` runs git and reads objects out of a repository, and `sanitize_rules.py` holds the three rule sets and the small predicates they need. The three helpers carry an underscore because a hyphenated name cannot be imported; the command puts its own directory on `sys.path` first, so it works from any working directory and from the hook, which calls it by absolute path.

Test sources never contain a leak-shaped literal. The kit's own `--all` run scans them, so a home path or an address written out in a test would fail the repository; the sandbox assembles them from pieces instead, and the whole-file waiver marker is built from two pieces as well so the test files do not read as waived. The wrapper tests execute both hooks through Git Bash, resolved the way `scripts/doctor.py` resolves it (`git --exec-path`, then its parents, then the two standard install paths, never a bare `bash` on PATH, which on Windows may be WSL), and skip with a printed notice when there is no bash to run them with.

Dropped from the original rule list: drive-letter absolute paths outside marked OS examples. The kit documents Windows installs with example paths such as `C:\Repo\my-app` on nearly every page, so that rule would have produced waivers and no signal. The home-path rules cover the case that actually leaks, which is a path carrying a person's account name.

## Acceptance

Four suites, 71 tests, every one of them running against a sandbox git repository whose config is empty so the machine cannot answer for it. The nine wrapper tests run when Git Bash is present and print a skip notice with the reason when it is not. Nothing below is claimed without a test behind it.

- Rules: the seeded fixtures (a Windows home path in shell form and twice in JSON form, a mac and a linux one, an email, three tracker org URLs, a private key header, a connection string, a GitHub token) each fail with their own rule id and nothing else, on the exact summary line the run prints, and the placeholder fixture passes a scan whole. A committed rule line with no tab, no id or no pattern is a hard failure.
- Denylist: a seeded term is caught and appears in neither stdout, stderr nor `--json`; it is caught in `AcmeViewModel`, `ACME_API_ID`, `acme_app_id`, `MyAcmeThing`, `acme-app`, `acme/x`, `Acme.kt`, `XAcmeClient`, `v2AcmeClient`, `ACMEapp` and `ACMEApp` spellings, and not inside `acmeish`, `ACMEISH` or `preacme`, which are scanned and reported clean. The two documented glued-capital misses are asserted as clean with the file counted as scanned, so the limitation cannot change without the test saying so. A four-letter term that is also the head of ordinary words has its own table: `ACHEPoint` and `ACHE_KEY` are findings on their own line numbers, while `CACHED value`, `a headache`, `ACHEISH` and `the cache` are clean. A `regex:` entry that does not compile is exit 2 with the term absent from both streams, and one whose quantified group is quantified again is exit 2 naming the rule number, while an ordinary `regex:` line with a group and an optional separator still loads and still catches.
- Redaction: a generic finding sharing a line with a private one prints `redacted`, a waiver reason is never printed, a private path prints as `<redacted path>`, a scan that reaches `.sanitize/` scans nothing there, and a path argument into it is exit 2. Each of those asserts the term is absent from both streams.
- Names: a private term in a file name and in a staged path is caught with a clean body, an address in a file name is reported as a name finding, and in a range both the path a blob was renamed away from and a second path sharing one blob are name-scanned.
- Allowlist: a placeholder does not clear a longer name, an allowed domain does not clear a longer domain, an ssh remote does not exempt the org, and a credential shape is never cleared.
- Waivers: a per-rule waiver suppresses and is counted; the whole-file waiver skips the file under `fixtures`, and is `waiver-abuse` with the file still scanned when it is outside `fixtures` or below the first line. A fixture carrying the whole-file waiver on its first line and a private term on the next is still a finding, while the generic leak on the line after it stays suppressed. A per-line waiver naming a private rule is `waiver-abuse` plus the private finding, with nothing counted as waived, both inside a `fixtures` directory and outside one.
- Scan modes: staged contents, a commit message in a range, an annotated tag message, a blob added and deleted inside the range, only the ref names passed with `--ref-name`, `--messages-only` skipping the tree, a zero remote sha, and an unknown remote sha falling back with a notice.
- What a pushed ref publishes: a tag pointing at a blob is a finding on the blob, a tag pointing at a tag is a finding in the inner tag's message, a tag whose tagger line carries an address is a finding on that line, and a tag pointing at a tree is a finding on both a path under it and the body of another file under it. None of the four publishes a commit that carries the term, so all four passed clean before the dispatch existed. A forged tree assembled with `git mktree`, carrying an empty subdirectory named with the term, is a `private-path` finding, which is the entry no `ls-tree -r` would have reported. A history that committed the denylist and took it back out with `git rm --cached` is exit 2 in a range and exit 2 again through a tag pointing at the tree that holds it, with the working tree tracking one clean file in both cases.
- Output encoding: a fixture path with three CJK characters is reported with the console encoding variables removed from the environment and the output piped, which is the cp1252 case, and both the checker and the pre-push wrapper finish clean with no traceback. A report of 4001 findings written into a pipe whose reader closes after one line exits 1 with neither a traceback nor an ignored-exception block on stderr.
- Failing loudly: a tracked denylist, a path that does not exist, and a git call that fails are each exit 2 with a message.
- Hooks: install writes when no hook is there, rewrites its own, refuses a foreign hook and a managed `core.hooksPath` without writing, and uninstall removes only ours. Both wrappers are executed through Git Bash, when it is present, with the stdin git feeds them: a dirty range blocks, a clean range passes, a new branch is scanned, an annotated tag message on an otherwise clean history blocks, a deletion is skipped, two refs are scanned in one push, a stripped PATH fails closed, a non-ascii path passes through both wrappers, and the pre-commit wrapper blocks a staged leak.
- A full `--all` run of this repository is green, with waivers only on the seeded fixtures, and every fixture carries its waiver on its first line.
