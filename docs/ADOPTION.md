# Adopting the kit in an existing repository

## Company rules come first

Most repositories are not empty. They already carry instruction files, git hooks, a lint and format setup, a CODEOWNERS file, and a way of working the team agreed on long before anyone tried a coding agent. This kit is a personal tool that has to fit inside all of that, so the rule it is built on is simple: it never overwrites and never deletes a file it did not write itself, and every write it does make is backed up first and can be undone with one command. If your company forbids AI tooling in the repository, or has not decided yet, you can still install it and keep every file it adds out of the history with a single switch.

The installer knows which files are its own because it records a sha256 per file in a managed-file manifest at `<kit home>/.kit-manifest.json`. A file that matches its record is a kit file nobody touched, so it is safe to refresh. A file that differs both from the record and from the version the kit is about to write belongs to you: it is backed up, kept exactly as it is, and the kit version lands beside it as `<name>.new` for you to read and merge by hand. A file that is already byte for byte the kit's version is the kit's file whatever the record says, so it is left alone and put back on the record, which is how a manifest you deleted or a broken one moved aside repairs itself on the next run.

## The order to do it in

1. `python scripts/doctor.py` checks the machine has what the kit needs, and fails only on a missing required tool.
2. `powershell -ExecutionPolicy Bypass -File .\install.ps1 -DryRun` prints the whole plan, one line per file, and writes nothing at all, not even the manifest. Read it. The plan is the whole truth about what a real run would do.
3. `powershell -ExecutionPolicy Bypass -File .\install.ps1` runs the plan. It ends by naming the backup folder it created and the exact command that rolls the run back. Keep that line.
4. For a repository, add the project scope: `powershell -ExecutionPolicy Bypass -File .\install.ps1 -Project C:\Repo\my-app -DryRun` first, then the same command without `-DryRun`. Project scope opens with an adoption preflight that lists what the repository already has and what the installer will do about each of those files.
5. `-LocalOnly` on the project run adds the paths that run manages to the repository's exclude file, so nothing it wrote can reach the team's history by accident. `CLAUDE.md`, `CLAUDE.project.md` and the files under `docs/` are listed one by one, and everything under `.claude/` is written as the single folder line `.claude/`, which also hides anything the team later adds inside that folder. It asks git where the exclude file is, so it works the same in a plain clone, a worktree and a submodule. Recommended for any repository you share, at least until the team has decided.

## What the kit writes, and what it never touches

User scope writes inside the kit home only, which is `%USERPROFILE%\.claude` or whatever `$KIT_HOME` points at: `skills/`, `hooks/`, `agents/`, `tools/`, `statusline.ps1`, `claude-account.ps1`, `merge-settings.py`, `CLAUDE.md`, `settings.json`, plus its own `.kit-manifest.json` and `backups/`. Nothing outside that folder.

Project scope writes three things: `CLAUDE.md`, `CLAUDE.project.md` and `.claude/` (the local settings and the branch hooks, plus the kit's agent definitions when you pass `-Sdd`), and a fourth on the runs you pass `-Sdd` to: `docs/`, the spec tree. Every run says which of those it is about to write before it plans anything, and `-LocalOnly` hides what it wrote, `docs/` included. It never writes a git hook, never sets `core.hooksPath`, never adds a CI file, never edits `.gitignore`, `.editorconfig`, `CODEOWNERS`, `CONTRIBUTING`, `.pre-commit-config.yaml`, `lefthook.yml`, `.husky/`, `.cursor/` or `.github/`. It reports those files in the preflight so you can see that it saw them, and then leaves them alone.

Nothing is ever deleted, in either scope, with or without `-Force`.

## How it adapts to what you already have

An existing `CLAUDE.md` stays exactly as it is and the kit version arrives as `CLAUDE.md.new`. Merging is a human job: your company's rules are the ones that matter, and the kit's file is a set of suggestions to lift from, not a replacement. The same holds for `settings.json`, `settings.local.json`, the hooks and the agent templates. When you have merged what you want, delete the `.new` file; nothing depends on it. The proposal itself is governed by the same rule: if a draft of your own already sits at that name, it is backed up before the kit version takes the place, and a rollback brings your draft back.

Your git hooks are untouched, whether they live in `.git/hooks`, in a `core.hooksPath` folder, or under husky or pre-commit. The installer only lists them. Any hook this kit ever ships is opt-in, installed by a command you run on purpose, and it must refuse to replace a hook that already exists or to write into a repository that has set `core.hooksPath`, because that hook belongs to whatever tool manages it. The sanitization guard planned in `docs/03-features/F10-sanitization-guard.md` follows that rule.

A second run is not a second install. Files the kit wrote and nobody changed are refreshed to the current version, after a backup. Files you edited keep your edits, and the proposal beside them is only rewritten when the kit version has moved on. Files that already match are skipped in silence. A run that finds nothing to do writes nothing, leaves no backup folder, and says so; the one thing it still writes is the record, and only when the record had lost a file it can see is its own. Run it as often as you pull.

## How to roll back

Every run that wrote anything leaves a folder under `<kit home>/backups/<stamp>/` holding a copy of each file it replaced, plus a `manifest.txt` recording what it overwrote, what it created, which files of yours it kept, and which `.new` proposals it left behind. Each line is written and flushed before the change it describes, which is what makes a half finished run recoverable.

A run stopped by a locked file or an error still reaches its own reporting: it says it did not finish, names the backup folder and prints the command that rolls it back. A run killed from outside, by Ctrl+C at the console or by `Stop-Process` or by closing the window, prints nothing and never gets to update the managed-file manifest, but the backup folder is on disk with every line it had written by then: `kit-restore.py --list` shows that stamp with the number of files it holds, and rolling it back puts those files back. The copies hold your bytes, not your Windows file attributes, so a file that was read-only comes back writable.

```
python scripts/kit-restore.py --list
python scripts/kit-restore.py --stamp 20260828-101500 --dry-run
python scripts/kit-restore.py --stamp 20260828-101500
```

The restore puts the overwritten files back, removes the files that run created, drops their entries from the manifest, names the files it recorded as yours and leaves them untouched, and leaves the `.new` proposals in place after naming them. A file the record says you changed after the backup was taken is never touched: the run names it, says why it skipped it, and exits 1. Pass `--force` when you mean it anyway. A file something else is holding open, or one you marked read-only, gets the same kind of answer: the run names it, carries on with the entries after it, and exits 1, so one file nothing will let go of never costs you the rest of the rollback. Three things can happen to such a file and the line tells you which. A file the run cannot read is a file whose bytes it cannot account for, so on a plain run it is skipped, saying it could not read the file to compare and naming the flag that overrides that. With `--force` it is put back, because replacing a file never required reading it. And when the replacement itself is refused, by a lock or by the read-only bit, the file is named as locked or unreadable and nothing about it changed. That last one is a guarantee rather than a hope: the restore never opens a file of yours for writing at all. It writes the bytes it is putting back into a temp file in the same folder and renames that over the target, so a write that cannot finish costs the temp file, which is cleaned up on the way out, and nothing else. When the record itself never got the file, which is what a run killed from outside leaves behind, the line in the backup is the record: the overwritten file is put back from the copy beside it, and a file that run created is removed only after a copy of it goes into the backup folder, so a rollback still takes nothing away for good. That line names the path the copy went to, and says whether the bytes it took were still the ones the run wrote, whether the file was edited since, or whether there was no copy to compare against and the bytes are simply unknown. The backup folders themselves are never deleted by the tooling; prune them yourself when you no longer want them.

By hand, without the script, the complete list is short. In the kit home, remove `skills/`, `hooks/`, `agents/`, `tools/`, `statusline.ps1`, `claude-account.ps1`, `merge-settings.py`, `CLAUDE.md`, `settings.json`, `.kit-manifest.json` and `backups/`, restoring anything you want to keep from a backup folder first. In a project, remove `CLAUDE.md`, `CLAUDE.project.md`, `.claude/` and, if you scaffolded it, `docs/`, and delete the lines the installer appended to the exclude file, which is the one `git rev-parse --git-path info/exclude` prints. That is everything it can ever write.

## Talk to your team

An agent that reads your repository and writes files in it is a tooling decision, not a personal preference, and plenty of companies have a policy on it already: which tools are allowed, whether their config files may be committed, what may be sent to a third party, and who reviews what the tool produced. Ask before you commit any file this kit added. Until you have an answer, run the project scope with `-LocalOnly` and everything the kit wrote stays on your machine, invisible to `git status` and to your teammates. When the answer comes, committing the files is a normal pull request like any other, and the rules in `CLAUDE.md` are a good thing to review together rather than to merge quietly.
